# NetBird Self-Hosted API Manager

## 1. Среда выполнения и стек
- **Рабочая директория:** `/home/artem/projects/netbird`
- **Интерпретатор Python:** строго `.venv/bin/python` (Python 3.15, управляемый через `uv`). Никогда не используй системный `/usr/bin/python3` для запуска скриптов проекта.
- **Установленные зависимости:** `requests`, `python-dotenv`.
- **Базовый клиент:** все HTTP-запросы к API должны выполняться через модуль `scripts/nb_client.py` (функции `request()` и `backup_resource()`).
- **Ответы NetBird:**В ответах NetBird API списочные поля (sources, destinations, groups) могут возвращаться как null (None). Всегда используй конструкцию (item.get("field") or []) вместо item.get("field", []).

## 2. Подключение к NetBird API
- **Конфигурация:** URL сервера и токен берутся исключительно из `.env` (`NETBIRD_URL` и `NETBIRD_TOKEN`) средствами `python-dotenv` внутри Python-скриптов.
- **Запрет на чтение секретов:** никогда не читай содержимое файла `.env` напрямую и не выводи значение `NETBIRD_TOKEN` в консоль или логи.
- **Базовый префикс API:** `${NETBIRD_URL}/api`
- **Заголовок авторизации:** `Authorization: Token <NETBIRD_TOKEN>`

## 3. Спецификации OpenAPI (`docs/openapi/`)
Полные схемы эндпоинтов, параметров пути и JSON-структур запросов находятся в `docs/openapi/`:
- `docs/openapi/networks.yml` — сети (`/api/networks`), сетевые ресурсы (`/api/networks/{networkId}/resources`) и роутеры сетей (`/api/networks/{networkId}/routers`).
- `docs/openapi/peers.yml` — узлы (пиры) и их параметры.
- `docs/openapi/groups.yml` — группы пиров и ресурсов.
- `docs/openapi/policies.yml` — политики контроля доступа (ACL).
- `docs/openapi/routes.yml` — классические сетевые маршруты (Network Routes).
- `docs/openapi/dns.yml` — DNS-серверы и зоны.
- `docs/openapi/setup-keys.yml` — ключи регистрации.
- `docs/openapi/users.yml` — пользователи и токены.

### Правило сверки со схемами
Перед написанием или изменением любого скрипта **обязательно прочитай соответствующий `.yml` файл** из `docs/openapi/`, чтобы проверить:
1. Точный URI эндпоинта и обязательные параметры пути (`networkId`, `resourceId`, `routerId` и др.).
2. Обязательные поля (`required`) в теле запроса (`requestBody`) — например, `name`, `address`, `enabled`, `groups` для `NetworkResourceRequest` или `metric`, `masquerade`, `enabled` для `NetworkRouterRequest`.
3. Взаимоисключающие поля — например, в `NetworkRouterRequest` нельзя одновременно задавать `peer` и `peer_groups`.
4. Разрешение зависимостей по именам: при привязке групп или сетей всегда сначала запрашивай их актуальные ID через `GET`, чтобы избежать дублирования.

## 4. Правила безопасности и предохранители (CRITICAL)
1. **Обязательный флаг `--dry-run`:** каждый новый скрипт в `scripts/`, выполняющий мутирующие запросы (`POST`, `PUT`, `DELETE`), **обязан** поддерживать флаг `--dry-run`.
   - В режиме `--dry-run` скрипт выводит HTTP-метод, полный URL и отформатированный JSON-payload, но **не отправляет** сетевой запрос.
   - При тестировании и запуске любого нового скрипта **первый запуск всегда выполняется с `--dry-run`**. Боевой запуск без `--dry-run` допускается только после явного подтверждения пользователя.
2. **Автоматический бэкап перед изменением:** перед отправкой любого `PUT` или `DELETE` запроса скрипт обязан сначала выполнить `GET` целевого ресурса (или запустить `.venv/bin/python scripts/export_state.py`) и сохранить снимок в `backups/` с таймстампом.
3. **Защита от случайного удаления (`DELETE`):** перед любым `DELETE`-запросом выведи пользователю точные `id`, имена удаляемых ресурсов и их тип, и дождись явного подтверждения.

## 5. Структура проекта и стиль кода
- `scripts/nb_client.py` — общий HTTP-клиент и утилиты резервного копирования.
- `scripts/export_state.py` — read-only выгрузка текущего состояния сервера в `backups/`.
- `scripts/manage_network_resources.py` — создание (`create`), обновление (`update`) и удаление (`delete`) сетевых ресурсов-подсетей (`/api/networks/{networkId}/resources`) по именам сетей и групп в произвольном регистре. Поддерживает флаги `--network`, `--name`, `--address`, `--groups`, `--dry-run` и `--yes` (перед `PUT` и `DELETE` автоматически сохраняет бэкап в `backups/`).
- `scripts/manage_*.py` — скрипты управления конкретными сущностями (должны иметь `argparse`, `--dry-run`, понятный вывод в stdout и обработку `requests.HTTPError` с выводом тела ответа сервера при статусах `400`/`422`).
- `backups/` — директория снимков конфигурации (игнорируется Git).

## 6. Готовые скрипты в проекте (`scripts/`)
Перед созданием нового скрипта проверь, нельзя ли использовать или доработать существующий:
- `scripts/nb_client.py` — базовый HTTP-клиент (`request(method, endpoint, payload)`) и функция авто-бэкапа `backup_resource(name, data)`.
- `scripts/export_state.py` — read-only выгрузка полного снимка (Networks, Resources, Routers, Groups, Policies) в `backups/netbird_state_*.json`. Поддерживает флаг `--markdown`.
- `scripts/export_networks_pdf.py` — генерация стилизованного PDF-отчета по сетям, роутерам, ресурсам и связанным политикам через `wkhtmltopdf`. Поддерживает флаги `--output <путь>` (по умолчанию `backups/netbird_networks.pdf`) и `--keep-html`.
- `scripts/manage_network_resources.py` — создание (`create`), обновление (`update`) и удаление (`delete`) сетевых ресурсов-подсетей (`/api/networks/{networkId}/resources`)

## 7. Интерактивный режим создания/изменения ресурсов (Wizard-режим)
Если пользователь ставит задачу в свободной форме без полного набора параметров (например: «создай подсеть 10.255.250.0/24»), веди диалог в формате пошагового опроса:

1. **Сбор обязательных полей по очереди:**
   Для команды `create` нужны 4 поля: `address` (IP/CIDR/домен), `network` (сеть), `name` (имя ресурса), `groups` (одна или несколько групп). Опционально — `description`.
   - Если каких-то полей не хватает, не запускай `create` и не придумывай значения — задай короткий вопрос по следующему недостающему параметру (например: *«Укажите сеть (network)»*).

2. **Нечёткий поиск и подтверждение совпадений:**
   - Когда пользователь вводит фрагмент имени сети или группы (например, `corp` вместо `Corp-LAN` или `bab` вместо `Baburka`), выполни `.venv/bin/python scripts/manage_network_resources.py lookup --query "<ввод>"`.
   - Если найдено точное совпадение — принимай его сразу и переходи к следующему вопросу.
   - Если найдено частичное совпадение (подстрока) — обязательно переспроси: *«Найдена сеть `Corp-LAN`, использовать её?»* (или выведи нумерованный список кандидатов, если их несколько).

3. **Финальная проверка через `--dry-run`:**
   - Когда все 4 поля собраны и подтверждены, сначала запусти `manage_network_resources.py create ... --dry-run`, покажи сформированный Endpoint и JSON-payload и запроси подтверждение перед отправкой на сервер.
